3. FINDINGS (ORDERED BY SEVERITY)
================================================================================
[HIGH-1] Logout uses unsigned JWT decode for user lookup
- Backend file: `backend/src/controllers/authController.js`
- In `logout`, backend uses `jwt.decode(refreshToken)` (not `jwt.verify`) and
  clears `User.refreshToken` by decoded `id`.
- Risk:
  A forged cookie payload with arbitrary `id` can invalidate another user's
  stored refresh token if attacker can submit crafted cookie values.
- Cross-layer impact:
  Frontend assumes logout is session-local/safe; backend can perform token
  revocation based on unverified payload.

[MEDIUM-2] Session restoration depends on frontend access token presence
- Frontend files: `frontend/src/context/AuthContext.jsx`,
  `frontend/src/pages/Orders.jsx`, `frontend/src/pages/ProfileSetup.jsx`,
  `frontend/src/pages/Payment.jsx`
- Behavior:
  Frontend initializes auth by checking localStorage access token and calling
  `/auth/me`. If token is absent, `isAuthenticated` stays false.
- Cross-layer mismatch:
  Backend session can still be valid via refresh cookie, but frontend protected
  pages redirect to `/login` before any request triggers refresh.
- Result:
  User may be forced to login again even with valid refresh token cookie.

[MEDIUM-3] Cookie policy may break refresh flow in cross-site production setups
- Backend file: `backend/src/controllers/authController.js`
- Cookie config uses `sameSite: 'strict'` for refresh token.
- Cross-layer mismatch:
  Backend CORS explicitly supports cross-origin credentials, but strict SameSite
  blocks cookie send in true cross-site deployments.
- Result:
  Refresh route may fail silently across different site origins.

[MEDIUM-4] Profile input validation differs between frontend and backend
- Frontend file: `frontend/src/pages/ProfileSetup.jsx`
- Backend file: `backend/src/controllers/authController.js`
- Frontend enforces alpha/spaces name format.
- Backend `updateProfile` checks only presence; no Joi schema and no strict
  alphabetic constraint.
- Cross-layer impact:
  Non-frontend clients can persist names that frontend rejects, causing data
  quality inconsistency.

[MEDIUM-5] Services over-fetching remains unresolved
- Frontend files:
  `frontend/src/components/ACServicesModal.jsx`,
  `frontend/src/components/WaterTankServicesModal.jsx`
- Backend file: `backend/src/controllers/serviceController.js`
- Both modals fetch all services; backend has no category query filter.
- Impact:
  Works functionally but scales poorly and transfers unnecessary data.

[LOW-6] Protected route strategy is duplicated and easy to miss
- Frontend files:
  `frontend/src/pages/Orders.jsx`,
  `frontend/src/pages/Payment.jsx`,
  `frontend/src/pages/ProfileSetup.jsx`
- Auth guard is per-page `useEffect` redirection instead of shared route guard.
- Backend still enforces auth, so this is not a direct security break.

[LOW-7] 429 handling is specialized for OTP but generic elsewhere
- Frontend files: `frontend/src/context/AuthContext.jsx`,
  `frontend/src/pages/*` API handlers
- Backend has global rate limiting (`express-rate-limit`) on all routes.
- Frontend has explicit retry UX for OTP 429 only; other endpoints mostly show
  generic failure messages.

[LOW-8] Flow state loss in OTP/profile setup can break long auth journey
- Frontend files:
  `frontend/src/pages/VerifyOtp.jsx`,
  `frontend/src/pages/ProfileSetup.jsx`
- Both depend on `location.state`; refresh loses state and can redirect users
  out of intended flow.

4. SECURITY & AUTH FLOW REVIEW
================================================================================
What is good
- Access token is short-lived (15m), refresh token rotation is implemented.
- Refresh mutex queue in frontend avoids duplicate refresh storms.
- Protected APIs enforce JWT via backend middleware.
- Admin routes enforce both `protect` and `authorize('admin')`.

Risks to prioritize
- [HIGH-1] unsigned decode during logout (token revocation integrity flaw)
- [MEDIUM-2] no proactive refresh-based session bootstrap in frontend
- [MEDIUM-3] strict SameSite in cross-site deployment scenarios
